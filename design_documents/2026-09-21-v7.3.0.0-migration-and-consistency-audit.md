# ShanaEncoder v6.0.1.4 → 7.3.0.0 迁移评估 + 预设一致性审计修复

## 生效日期

- `2026-09-21`

## 背景

用户把 ShanaEncoder 从 v6.0.1.4 升级到了 7.3.0.0（安装目录从 `D:\software\ShanaEncoder v6.0.1.4 免安装版` 变成了 `D:\software\ShanaEncoderV7.3.0.0`），问这个仓库里的自定义预设（欧美/日本成人片压制用，libx265 CPU / hevc_nvenc / hevc_qsv 多条产线）是否需要跟着做改动。

这份文档记录完整的调查过程、每一处发现、以及最终落地的两轮改动（对应两个 git commit）的具体依据，避免这个仓库变成"改了什么、为什么改"说不清楚的黑盒。

## 调查方法

1. 对比 `舟 6.0原预设`（v6.0.1.4 的预设留档）与当前自定义预设的 XML schema，确认标签结构有没有变化。
2. 直接检查 7.3.0.0 安装目录本身（presets 文件夹的上一级 `D:\software\ShanaEncoderV7.3.0.0`）：找更新日志、找安装包自带的出厂默认预设、找有没有独立的 `ffmpeg.exe` 可以查版本号。
3. 跑仓库自带的 `/audit-presets` 技能，全量审计 32 个自定义预设文件夹、341 个 XML 文件的一致性——这一步跟版本升级本身没有直接关系，是为了把"到底要不要改"这个问题回答得更有把握，顺带做的。

## 发现 1：Settings XML schema 完全兼容，不需要重写任何预设

`舟 6.0原预设` 与当前所有自定义预设用的都是同一套 10 标签结构：

```
inputparamBox / prefixtextBox / extensiontextBox / filterparamBoxV / filterparamBoxA /
encparamBox / x264optsBox / substyle / fontnameSE / Logo（12个子标签）
```

`encparamBox` 里装的是原始 ffmpeg 命令行参数字符串，ShanaEncoder 只是原样透传给底层编码引擎，跟 GUI 版本无关。**结论：所有自定义预设 XML 本身不需要因为升级而改内容。**

## 发现 2：7.3.0.0 新增了 `<tonemapParam>` 标签（HDR 相关，本仓库暂不需要）

7.3.0.0 安装包自带的 124 个出厂默认预设（`Apple`/`Cowon`/`(Convert)`/`(Stream Copy)` 等文件夹）全部带有一个新标签 `<tonemapParam>`，是一段 HDR→SDR 的 tonemap 滤镜链，配合 `shanatonemap` 自定义滤镜使用，例如：

```
zscale=transfer=linear:npl=100,format=gbrpf32le,zscale=primaries=bt709,tonemap=tonemap=hable:desat=0,zscale=transfer=bt709:matrix=bt709:range=tv,format=yuv420p
```

用户确认片源基本是 SDR（欧美/日本成人片，不是 HDR10 拍摄），所以**没有**往自定义预设里加这个标签，只在 [CLAUDE.md](../CLAUDE.md) 里留了一笔说明，方便以后真遇到 HDR 素材时知道去哪参考。

## 发现 3：因改目录名而真实失效的硬编码路径（这是唯一"必须改"的、直接由升级引起的问题）

安装目录改名后，仓库里有 4 处硬编码了旧路径 `D:\software\ShanaEncoder v6.0.1.4 免安装版\presets`，全都是真实会报错的问题，不是猜测：

| 文件 | 问题 |
|---|---|
| `diag.ps1` | `$presets = '旧路径'`，今天重跑会直接报路径不存在 |
| `diag2.ps1` | 同上 |
| `generate_phase1.ps1` | 同上 |
| `AGENTS.md` | 指向 `PRESET_POLICY.md` 的链接用的是旧绝对路径 |

修法：三个 `.ps1` 脚本把 `$presets` 改成 PowerShell 内置变量 `$PSScriptRoot`（脚本自动定位到自己所在目录），`AGENTS.md` 的链接改成仓库内相对路径。这样以后再升级版本、目录名再变，也不会重蹈覆辙。

`position.txt`（内容是 `D:\tools\ShanaEncoder v6.0.1.4\presets`）**没有改**——它是记录 `舟 6.0原预设` 文件夹历史来源的备忘，本来就该指向旧版本。

排查安装目录时，用来调查的子代理误执行了 `git add`，把 7.3.0.0 安装程序自带的出厂默认预设文件夹（`Apple`/`Cowon`/`Eduplayer`/`HTC`/`Invio`/`Iriver`/`LG`/`Mando`/`Samsung`/`Sony`/`YujinPNP`/`(Convert)`/`(Stream Copy)`，共 124 个文件）暂存到了 git。已发现并撤销暂存，之后加进 `.gitignore`——这些是安装包产物，不是这仓库自己的工作成果，重装/升级 ShanaEncoder 时会自动重新生成，不需要进版本库。

## 关键参数说明：`-movflags faststart` 是什么

MP4（含 MOV/M4A 等同族容器）文件内部有一段叫 `moov atom` 的元数据索引，记录着关键帧位置、时长等播放器需要的信息。FFmpeg 默认把 `moov` 写在文件**最后面**（因为编码时要等所有数据都写完，才知道每一帧最终的字节偏移量）。

这带来一个实际问题：播放器/浏览器如果是**边下载边播**（网络流式播放、NAS/群晖等设备上的 DLNA 播放、网页里的视频预览），必须先下载到文件末尾拿到 `moov`，才能开始播放——文件越大，等待越久，甚至可能要下载完整个文件才能开始。

加上 `-movflags faststart` 之后，ffmpeg 在编码完成后会多做一步：把 `moov` 从文件末尾搬到文件开头（`ftyp` 之后、`mdat` 之前）。这样播放器只要收到文件最开头的一小段数据就能拿到索引信息，可以立刻开始播放，不用等下载完。

代价：多了一次文件重写/搬运的开销（不是重新编码，只是移动元数据），耗时跟文件体积大致成正比，通常是几秒到十几秒级别，可以忽略不计。这也是为什么仓库里绝大多数会产出 MP4 的预设都统一带着这个参数——这次只是把 8 个"漏网"的预设家族（`nvQuality`、`qualityQsv`、`quality*TransTo*` 系列）补齐，让它们跟仓库里其他家族保持一致。

### 补充排查：`00_TEMPLATE_MASTER` 的两个母版也漏了

审计范围原本刻意排除了 `00_TEMPLATE_MASTER`（golden-master 模板，不会被 ShanaEncoder 直接加载，用来生成其他文件夹的预设）。用户追问"是不是所有配置都加了 faststart"之后，专门回头查了这 6 个母版文件，发现：

| 文件 | `-f mp4` | faststart（改前） |
|---|---|---|
| `cpu_fast_crf21.xml` | 有 | 有 |
| `cpu_medium_crf21.xml` | 有 | 有 |
| `filter_scale720p.xml` / `filter_scale1080p.xml` | 无（纯滤镜模板，不含完整 encparamBox） | 不适用 |
| `nvenc_cq23.xml` | 有 | **没有** |
| `qsv_cq23.xml` | 有 | **没有** |

`nvenc_cq23.xml`、`qsv_cq23.xml` 这两个 NVENC/QSV 母版跟之前修复的 8 个"漏网"家族是同一种模式——libx265 系全都带了 faststart，NVENC/QSV 系统一漏掉了。已经补上，跟另外两个 libx265 母版对齐。这两个文件是母版，不是仓库里"至今没修的遗漏"，但既然是将来生成新预设的源头，不修的话以后从这两个母版派生的新文件会继续带着同样的缺陷，所以一并修了。

### 用户追问"要不要给所有配置都加 faststart"：按容器格式分三类处理

用户的直觉是"代价小、收益大，干脆全加"。逐一核实后，`-movflags faststart` 其实是 ffmpeg **mov/mp4 复用器的私有参数**（mov、mp4、m4a、3gp、3g2、mj2 共用同一套复用器代码），只对这个家族的容器有意义；仓库里还有其他容器格式，不能一概而论：

| 容器 | 是否属于 mov 家族 | 处理方式 |
|---|---|---|
| MP4/MOV 视频 | 是 | 已在前面两轮全部补齐 |
| **M4A 音频**（`0压 音频复制流/复制为 M4A.xml` + `2压 音频预设` 里 6 个 HE-AAC 系列，共 7 个文件） | **是** | 技术上跟 MP4 视频同理，同样有"moov 放最后，边下边播要等"的问题，**已补上** `-movflags faststart` |
| MP3 / OGG / AC3 / FLAC / WAV（`0压 音频复制流`、`2压 音频预设` 剩下的文件） | **否**，各自是完全独立的容器格式 | **不加**。`-movflags` 是这些复用器不认识的参数，7.3.0.0 没有独立 `ffmpeg.exe` 可离线验证会被静默忽略还是直接报错；而且这几种格式本来就不存在"索引放最后"的问题（MP3/AC3 是逐帧可解码的流式格式，WAV 头部很小，FLAC 有自己的机制），加了也没有实际收益，纯粹是零收益冒风险 |

### 排查范围之外：`舟 5.X原预设` / `舟 6.0原预设`（历史留档，故意不动）

这两个文件夹分别是 47 个/24 个（编者注：以 `-f mp4` 计）mp4 输出预设，faststart 覆盖率是 0——但这是**故意**的：它们是 ShanaEncoder 5.X / 6.0 版本当年实际自带的出厂预设的原始留档，作用是保留"那个版本当时到底是什么样子"的历史快照，不是仓库正在维护的活预设。如果替它们补上现在的参数，这份历史记录就失真了，所以不碰。`舟 滤镜参考` 文件夹（15 个文件）本身就已经 100% 带 faststart，不需要改。
